#### 2.1 The Three-Layer Stack That Actually Works Most vendors sell a monolithic “AI orchestrator” that becomes a black box. Instead, isolate three layers:

1. **Routing Engine**: Stateless rules engine that decides which channel to push the customer to next. 2. **Context Store**: Low-latency key-value store that holds the entire customer journey (voice call transcript, prior chat logs, policy flags). 3. **AI Services Layer**: Microservices for intent detection, entity extraction, and decision models.

The architectural trade-off between latency and scalability is well-documented in distributed systems research. While a monolithic architecture minimizes latency—achieving near-instantaneous inter-service communication—it is highly vulnerable to performance degradation under load spikes, as evidenced by a Tier-2 carrier’s system collapse during Hurricane Ian in 2022, where a monolithic orchestration layer could not sustain 110,000 concurrent sessions (NIST, 2023). In contrast, a three-layer microservices stack introduces an overhead of 15–20ms per transaction due to inter-process communication and load balancing but demonstrates superior resilience, handling up to 480,000 concurrent sessions without degradation (IEEE, 2023). This performance differential underscores a critical trade-off in CX AI orchestration: latency can be sacrificed for scalability and fault tolerance, particularly in disaster recovery scenarios, where system uptime directly correlates with customer retention and regulatory compliance (FEMA, 2023). The architectural choice, therefore, must be dictated by the expected use case, with high-volume, low-latency demands requiring hybrid approaches or edge computing enhancements to mitigate latency penalties (Satyanarayanan et al., 2022).

#### 3.2 Build a Data Mesh for the Context Store I’ve reviewed two carriers that built a single monolithic database for their Context Store. Both melted under load. Instead, use a **data mesh**:

- **Domain Owners**: Each system (PAS, Loss Run, CRM) owns its data model. - **Event Log**: All changes are streamed via Kafka topics. - **Materialized Views**: The Context Store reads from these views, not the raw streams.

Example schema for the Context Store (PostgreSQL JSONB):

```sql CREATE TABLE journey_context ( correlation_id UUID PRIMARY KEY, customer_id VARCHAR(36) NOT NULL, journey_state JSONB NOT NULL, last_updated TIMESTAMPTZ NOT NULL DEFAULT NOW(), policy_flags JSONB, loss_history JSONB, media_urls TEXT[], INDEX idx_customer_id ON journey_context(customer_id), INDEX idx_last_updated ON journey_context(last_updated) ); ```

Resource estimate: **2 data engineers x 12 weeks** to build the mesh. Add another **4 weeks** if your PAS doesn’t already emit events.

### 4. Deploy AI Models That Don’t Poison the Journey

#### 4.1 Start with Two Models: Intent and Entity Extraction Most orchestration projects over-engineer. Start with these two models only:

- **Intent Detection**: Classifies customer utterance into FNOL, billing, coverage question, etc. Use a **fine-tuned BERT model** (e.g., `bert-base-uncased` + your own labeled dataset). - **Entity Extraction**: Pulls out policy number, claim type, date of loss. Use **spaCy’s `en_core_web_lg`** with custom rules for insurance jargon.

Do not build a separate model for sentiment. Sentiment is a lagging indicator; intent is predictive. Add sentiment later if you have spare GPU budget.

The spaCy entity extraction model initially exhibited significant performance limitations due to domain-specific linguistic complexities. Upon closer examination, it became evident that initial training data assumptions were misguided, as adjusters’ notes contained substantial colloquialisms—such as "fender bender" denoting minor accidents or "totaled" indicating severe vehicular damage. These discrepancies led to systematic misclassifications, particularly evident in cases where "total loss" claims were erroneously categorized as "glass repair" due to the model’s association of "windshield" with "glass." This failure necessitated a comprehensive rebuild of the training corpus, incorporating 5,000 additional labeled examples, with particular emphasis on edge cases such as UK-specific phrasing ("my car is a write-off") and US slang ("it’s toast"). The vendor-provided "pre-trained" model, optimized for general customer service datasets (cf. *Honnibal et al., 2020*), proved inadequate for insurance-specific lexicon, necessitating domain adaptation. This case underscores the critical importance of validating NLP models against real-world, uncurated datasets rather than relying solely on clean, curated benchmarks, a finding consistent with prior research on domain-specific NLP challenges (*Gurulingappa et al., 2012; Dernoncourt et al., 2017*).

### 5. Build the Channel Router That Doesn’t Leak Customers

#### 5.1 Rule Engine: JSON + Redis for 100ms Routing The router architecture must achieve sub-100ms decision latency to meet real-time processing requirements. This necessitates the use of an in-memory data structure store, such as Redis, for efficient JSON-based rule evaluation and routing logic. The Redis-backed approach aligns with established high-performance routing frameworks documented in prior systems research, including those leveraging Redis for stateful microservices (e.g., *Carlson, 2013; Zaitsev, 2017*). The JSON schema design must accommodate complex conditional routing logic while ensuring minimal serialization overhead, a consideration previously explored in studies on high-throughput JSON processing in distributed systems (*Palkar et al., 2018; Apache Druid Contributors, 2021*).
